# MAPro 服务端网页版本地测试 & KOL 投放能力调研

> 调研目标

## 一、本地 mac 预部署测试指南

### 1.1 前置准备

- 已安装 Bun（建议 1.2.5+，与 CI 一致）
- 已执行 `bun install`
- 已确认 `.env` 或环境变量按需配置（见下方常用变量）

常用环境变量（本地测试时可写在命令行或 `.env`）：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `MAPRO_WEB_PORT` | `3000` | Web HTTP 端口 |
| `MAPRO_WS_PORT` | `8081` | WebSocket 端口 |
| `MAPRO_WEB_HOST` | `127.0.0.1` | 监听地址；如需局域网访问，设为 `0.0.0.0` |
| `MAPRO_DATA_DIR` | `~/.mapro` | 数据目录（SQLite、配置、工作区） |
| `MAPRO_WEB_UI_DIR` | `../web-ui/dist` | 前端静态资源目录 |
| `MAPRO_TRUST_PROXY` | - | 设为 `1` 可模拟反向代理场景 |
| `NODE_ENV` | - | 设为 `production` 可触发生产环境行为（HSTS、trust proxy 等） |

### 1.2 构建前端

```bash
cd /Users/chaihao/LLM/ma-proma
bun run --filter=@ma-proma/web-ui build
```

构建产物位于 `apps/web-ui/dist/`。

### 1.3 启动服务端

```bash
# 方式 A：使用 workspace filter
bun run --filter=@ma-proma/web start

# 方式 B：直接进入目录启动
cd apps/web
bun run start
```

服务启动后会监听：
- `http://127.0.0.1:3000` — 前端页面 + REST API
- `ws://127.0.0.1:8081` — WebSocket（Chat / Agent）

### 1.4 快速验证

```bash
# 1. 健康检查
curl http://localhost:3000/health

# 2. 首次使用需 setup 管理员
# POST /auth/setup

# 3. 登录获取 access token
# POST /auth/login

# 4. 带 Token 请求 Campaign 列表
curl -H "Authorization: Bearer <token>" http://localhost:3000/api/campaigns

# 5. 直接运行项目自带冒烟测试
bun run scripts/smoke-test.ts
```

冒烟测试会完整跑通：健康检查、认证、Campaign CRUD、KOL 候选池、内容追踪、工作流推进、WebSocket Chat/Agent 未配置提示等。

### 1.5 更接近服务器环境的测试

mac 与真实 Linux 服务器差异主要在于：

1. **文件路径与权限**
   - 服务器通常使用 Linux 绝对路径，确保 `MAPRO_DATA_DIR` 指向可写目录。
2. **进程守护**
   - 本地按 `Ctrl+C` 即可停止；服务器建议使用 `systemd` / `pm2` / `docker`。
3. **反向代理 + HTTPS**
   - 本地可直接访问 `localhost:3000`；服务器通常前面有 Nginx/Caddy。
   - 测试反向代理场景：
     ```bash
     MAPRO_TRUST_PROXY=1 bun run --filter=@ma-proma/web start
     ```
4. **持久化数据**
   - 本地默认用 `~/.mapro`；服务器应挂载独立数据卷。
5. **Docker 化验证（推荐）**
   - 项目根目录已有 `Dockerfile`，可构建镜像后在 Linux 容器内跑一遍：
     ```bash
     docker build -t mapro-web:test .
     docker run -p 3000:3000 -p 8081:8081 mapro-web:test
     ```

### 1.6 上线前检查清单

- [ ] `bun run --filter='*' typecheck` 通过
- [ ] `bun test` 通过
- [ ] `bun run scripts/smoke-test.ts` 通过
- [ ] 前端 `apps/web-ui/dist/` 已生成且被服务端正确托管
- [ ] 环境变量已配置（端口、数据目录、API Token / JWT Secret）
- [ ] 数据库目录已持久化，不会被容器重建清空
- [ ] 反向代理已配置 `MAPRO_TRUST_PROXY=1` 或 `NODE_ENV=production`
- [ ] WebSocket 端口已在防火墙/安全组放行

## 二、抖音 / 小红书达人投放能力调研

### 2.1 平台官方生态概览

| 维度 | 抖音 | 小红书 |
|------|------|--------|
| 官方撮合平台 | **巨量星图** | **蒲公英平台** |
| 内容形态 | 短视频、直播、短剧 | 图文笔记、短视频 |
| 核心角色 | KOL（头部/腰部）、KOC、达人直播 | KOL、KOC、买手 |
| 计费模式 | CPT、CPS、CPM、按效果付费（到店核销/下单） | 定制合作、招募合作、共创合作（CPM）、优效模式 |
| 数据打通 | 抖音电商、巨量千川、直播 GPM 实时回传 | 聚光平台、乘风电商、薯条、店铺直播 |
| 核心优势 | 算法推荐、直播带货、短剧爆发 | 种草决策、搜索心智、长尾流量 |

### 2.2 官方 API 能力与接入门槛

#### 抖音 — 巨量星图 / 巨量引擎商业开放平台

开放能力（面向品牌主 / 认证服务商）：

- 获取星图客户任务列表
- 获取任务订单列表
- 获取订单投后分析报表（创意表现、传播表现、舆情表现、组件转化、性价比）
- 获取订单投后受众报表（性别、年龄、省份、城市、设备、兴趣、活跃度）
- 直播带货数据实时回传（GPM、实时转化率、观众画像波动）

接入门槛：

- 需巨量引擎 / 星图平台认证账号
- 部分数据接口仅向认证服务商开放
- 高阶能力（如实时转化回传）需完成电商数据授权

#### 小红书 — 蒲公英平台 OpenAPI

开放能力：

- 博主报价查询
- 定制合作下单、订单尾款支付、加热订单创建
- 订单状态查询、SPU/组件/跨域信息查询、品牌信息查询
- 投放后累计数据接口

接入门槛（2025 年规则）：

- 单一品牌近一年蒲公英消耗 > 500W；或
- 集团维度满足 2000W 消耗，且申请开通的品牌为新增或同比增长 ≥ 10% 的品牌（一个集团最多 5 个账号）
- 白名单按季度校验，不满足消耗且连续两季度环比下跌的品牌会被移除

> 结论：小红书官方 API 门槛极高，对中小品牌不友好；抖音相对开放，但高阶数据仍需服务商资质。

### 2.3 真实投放完整链路

一个可落地的达人投放项目通常分为 7 个阶段：

```
策略规划 → 达人筛选 → 建联/询价 → 合同/下单 → 内容生产 → 发布/加热 → 数据回收/复盘
```

#### 阶段 1：策略规划

- 明确目标：品牌曝光、种草、搜索占位、直播带货、转化
- 预算拆分：头部 KOL 引爆 + 腰部达人渗透 + KOC 口碑沉淀
- 平台组合：小红书做「种草/搜索」，抖音做「曝光/转化/直播」
- 内容方向：Big Idea、核心信息、内容 pillar、语气风格

#### 阶段 2：达人筛选

筛选维度：

- 基础数据：粉丝量、赞藏总量、阅读/播放、互动数、更新频率
- 内容质量：爆文率、互动率、完播率、粉丝粘性
- 粉丝画像：性别、年龄、城市、兴趣、与品牌 TA 匹配度
- 商业历史：过往合作品牌、合作频率、信用等级
- 性价比：CPE、CPM、历史带货数据
- 真实性：排除刷量账号（数据波动、粉丝画像异常、互动率异常）

#### 阶段 3：建联与询价

- 官方平台内邀约（星图任务 / 蒲公英订单）
- MCN / 达人经纪人间接合作
- 报价谈判：CPT、按效果分成、保底 + 佣金

#### 阶段 4：合同与下单

- 明确交付物：视频/笔记数量、发布时间、授权范围、素材使用权
- 平台内下单（走官方平台可保证合规与数据回流）
- 支付：定金 + 尾款，或平台担保交易

#### 阶段 5：内容生产

- 提供 Brief：品牌背景、产品卖点、目标人群、必须/禁止元素、参考案例
- 达人创作 + 品牌/ agency 审稿
- 合规审查：广告法、平台社区规范、违禁词、医学/美妆/食品特殊资质

#### 阶段 6：发布与加热

- 达人发布内容
- 平台内加热：抖音 Dou+、小红书薯条、聚光/千川追投
- 素材二次创作：优质达人内容剪辑为广告素材，撬动付费流量
- 评论区运营、舆情监控

#### 阶段 7：数据回收与复盘

- 传播数据：曝光、播放、点赞、评论、收藏、分享、完播率
- 互动数据：CPE、CPM、互动率、爆文率
- 搜索数据：品牌词/产品词搜索趋势、看后搜率
- 转化数据：进店 UV、加购、下单、GMV、ROI
- 人群数据：性别、年龄、城市、兴趣分布
- 复盘输出：达人分级、内容标签效果、投放结构优化建议

### 2.4 MAPro 当前已具备的能力

基于代码现状，MAPro 在达人投放链路上已覆盖：

- Campaign 项目创建与管理（目标、预算、周期、城市、TA、平台）
- 13 步标准工作流（市场分析 → 竞品 → 用户 → 品牌 DNA → 概念 → 目标 → 创意 → 平台矩阵 → KOL 金字塔 → KOL 搜索 → 候选池 → Brief → AB 测试）
- KOL 数据库与候选池管理
- Brief 生成与管理
- 内容审核（Content Audit）
- 内容追踪（Content Tracking）数据回收
- Agent 模式辅助策略与内容生产

### 2.5 还缺失的关键能力（按优先级排序）

#### P0：平台官方数据接入

| 能力 | 说明 | 依赖 |
|------|------|------|
| 抖音星图 API 接入 | 任务、订单、投后报表、受众分析 | 巨量引擎认证账号 / 服务商资质 |
| 小红书蒲公英 API 接入 | 博主报价、下单、订单状态、投后数据 | 高消耗门槛（500W/年） |
| 第三方数据平台接入 | 蝉妈妈、新红、灰豚、飞瓜等，作为官方 API 补充 | 购买第三方账号 / API |

> 若官方 API 短期无法接入，可先通过 **第三方数据平台 + 手动录入** 的方式跑通 MVP。

#### P0：真实 KOL 数据搜索与评估

- 接入抖音 / 小红书达人公开数据（粉丝、互动、内容标签、报价）
- 达人打分模型：内容匹配度、粉丝匹配度、性价比、真实性、合作历史
- 反作弊检测：异常粉丝增长、互动率异常、评论水军识别

#### P1：达人建联与询价管理

- 达人联系人 / MCN 信息管理
- 询价记录与报价对比
- 合作状态流转：意向 → 报价 → 谈判 → 签约 → 执行 → 结算

#### P1：合同与财务管理

- 合同模板与电子签集成
- 付款计划（定金/尾款/效果分成）
- 发票与结算记录
- 单达人 ROI 与项目总 ROI 计算

#### P1：内容发布与加热管理

- 发布排期日历
- 发布链接 / 内容 ID 采集
- 加热订单记录（Dou+ / 薯条 / 千川 / 聚光）
- 素材授权与二次创作管理

#### P1：舆情与评论监控

- 笔记/视频评论区监控
- 负面关键词预警
- 危机响应流程（48 小时整改机制）

#### P2：转化归因

- UTM 参数 / 专属优惠码 / 暗号追踪
- 电商后台数据导入（天猫、抖音小店、小红书店铺）
- 跨平台转化路径分析（小红书种草 → 抖音/淘宝收割）

#### P2：MCN / 供应商管理

- MCN 机构档案
- 达人归属关系
- 供应商评级与黑名单

### 2.6 推荐的 MVP 路径

如果目标是「先在真实业务中跑起来」，建议按以下顺序补齐：

1. **数据源**：先采购一个第三方数据平台（如新红/蝉妈妈）的账号，手动导出达人数据导入 MAPro；同时申请小红书/抖音官方平台权限。
2. **KOL 评估模型**：基于已有 KOL 数据库扩展字段（粉丝画像、互动率、报价、内容标签、信用等级）。
3. **合作流程**：在 Campaign 下增加「达人合作」子模块，记录从筛选到结算的全流程状态。
4. **内容追踪自动化**：目前内容追踪已存在，但需要支持从发布链接自动抓取公开互动数据（可先用爬虫/第三方 API）。
5. **财务与合同**：增加合同模板、付款计划、结算记录，先解决「钱怎么付、怎么算 ROI」。
6. **平台 API 对接**：在业务跑通后，再用官方 API 替代手动操作，提高效率与数据准确性。

### 2.7 合规与风险提示

- 小红书对非报备商业笔记打击严格，建议优先走蒲公英平台。
- 抖音星图是所有商业合作的官方通道，私下接单存在限流/封号风险。
- 广告法合规：医疗、美妆、食品、金融等类目有特殊资质与用语要求。
- 数据合规：爬取公开数据需注意平台反爬策略与法律边界；官方 API 是最安全路径。

## 三、下一步建议

1. **本地验证**：按照「一、本地 mac 预部署测试指南」完整跑一遍，确认 Web + Web UI 在 mac 上可运行。
2. **Docker 化验证**：构建 `Dockerfile`，在 Linux 容器内再跑一遍冒烟测试，提前暴露服务器环境差异。
3. **达人数据 POC**：选定 1-2 个第三方数据平台，导出 50-100 个抖音/小红书达人数据，验证 MAPro 的 KOL 筛选与评估模型是否够用。
4. **MVP 功能规划**：基于 2.5 的缺失能力清单，选择 P0/P1 能力进入产品迭代。
